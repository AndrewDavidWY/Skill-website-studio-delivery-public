# 阿里云 OSS 与 Let’s Encrypt

这是条件流程；仅在客户选择该技术方案且相应操作已授权时使用。下一次执行前核查当前官方 API 与工具版本。本文件不包含任何客户的真实凭据或可直接运行的生产发布脚本。

## OSS 发布

1. 读项目配置并确认账号身份、桶、区域、endpoint、域名绑定与对象清单；域名信息来自用户和控制台，不拼接猜测。已有凭据在允许范围内复用，不输出值，不硬编码其他项目的凭据路径。
2. 核对 DNS 与 OSS 自定义域名绑定是两个独立配置。更改 DNS 时保留 MX、TXT、邮件验证等非网站记录；根域名记录类型按 DNS 服务能力选择。[OSS 自定义域名说明](https://www.alibabacloud.com/help/en/oss/user-guide/access-buckets-via-custom-domain-names)
3. 检查桶 ACL、Bucket Policy、公共访问阻止和静态网站设置；先保存现有配置。不能因首页 403 就整桶开放：先确认桶是否专供公开站点，是否混放内部对象。
4. 专用公开站点桶可按需求仅授予匿名 GetObject；不授予匿名列举、写入或删除。策略须保留既有语句与约束。涉及阻止公共访问时只处理授权目标桶，不顺带修改账号全局设置。混合用途桶须设计限定前缀、分离目标或改用合适前端，不能套用 `bucket/*`。
5. 配置首页与错误页，再验证。对象 public-read 能让现有文件可读，并不保证无效路径会返回设计的 404。遇到 403，分别排查访问授权、错误页可读性与静态网站路由；修改后实测“缺失文件”和“缺失目录”，检查状态码及正文。
6. 仅上传已检查的构建目录，备份会覆盖的对象和必要响应头；保留远端旧文件，除非用户明确授权清理。写对 Content-Type、Content-Disposition 与缓存头。内容哈希资源适合长缓存，HTML 宜便于更新。
7. 逐域名检查首页、主要链接、静态资源、404；有视频则检查 Range 响应和实际播放。记录时间及错误，不仅保存“上传成功”。

静态站还要分别验证自定义域名的 `GET /`、`GET /index.html`、关键资源和不存在路径。对象地址可读不能证明根路由、静态网站托管或自定义域名映射正确；优先检查实际响应正文和状态，不用 `HEAD` 结果代替页面 GET。AccessDenied 不直接说明默认首页未设或整桶需要公开。结合控制台截图与实际 GET 证据，检查 IndexDocument、路由规则、对象/桶 ACL 与 Policy、DNS/CDN 回源及错误页。只有确实执行并核验授权变更后，才能报告已更改公开访问或持续权限。public-read 桶应只容纳公开站点资源，绝不用 public-read-write；公开设置不能保证桶内历史其他对象安全，先核对已有对象，备份存私有位置。

权限拒绝、目标不一致或混入非公开对象时停止相关变更并报告具体原因，不扩大权限重试。网络暂时错误可少量重试；先查已有对象和状态，避免重复覆盖或重复提交。

## Let’s Encrypt 申请

先检查域名的 HTTP、DNS/CAA、当前证书和本机工具，确定证书覆盖范围与联系邮箱；一个证书可覆盖根域名和 www，不必申请通配符。

### HTTP-01 适用时

域名已经能通过公网端口 80 读取本站临时文件时，可通过 OSS 完成 HTTP-01。验证文件必须位于 `/.well-known/acme-challenge/<token>`，不能被登录页、下载行为或错误重定向破坏。[Let’s Encrypt 验证方式](https://letsencrypt.org/docs/challenge-types/)

本地项目目录不是远程 OSS 的 webroot。只在本机运行 `certbot --webroot` 不会自动上传文件。可为 Certbot 使用 manual auth/cleanup hook，由 SDK 把当前验证 token 写入已授权桶，并检查公网响应。

钩子需约束域名、桶和挑战路径，拒绝异常 token，避免覆盖已有不相关对象；清理只删除本轮创建且内容匹配的文件。不能把账户私钥当验证文件上传。先用随机临时文件预检可访问性，随后清理；排错时可使用测试环境，测试证书不能交付为正式证书。失败先查原因与 CA 限制，不反复申请正式证书。

### 其他情况

HTTP 验证不可行或确实需要通配符时，选择 DNS-01。只维护所需 TXT 记录，不覆盖其他验证记录，不更改整个域名委派。若缺少 DNS 授权，则给用户准确记录值和下一步，等待实际验证后继续。

### 本地存储与校验

Certbot 的配置、工作和日志目录优先放用户私有配置位置。用户明确要求项目内存储或导出时，只使用隔离的私有目录；可导出 `<domain>.pem` 完整证书链与 `<domain>.key` 私钥，私钥权限限制为当前用户读取。加入版本控制忽略并检查构建与上传清单，确保不在 `public/`、`dist/` 或公开备份内；忽略规则不能代替上传检查。

校验 SAN 覆盖、有效期、签发者、证书与私钥公钥匹配；不打印私钥。续期应自动同步导出文件，保留 Certbot 账户及续期配置。[Certbot 使用与续期说明](https://eff-certbot.readthedocs.io/en/stable/using.html)

## 自动续期脚本交付

用户要求把 OSS + Let’s Encrypt 续期流程脚本化时，在当前项目建立 `ops/ssl-renewal/` 或沿用清晰的运维目录。脚本覆盖环境检查、证书续期、绑定、HTTPS 验证及所需调度；编号仅是可选组织方式。输出准确的执行状态，不能以退出成功代替实际签发或绑定证据。

本机脚本只读取私有配置文件；云端按下节安全注入配置。不把 DNSPod、阿里云密钥、证书私钥或 Certbot 账户状态写入源码、`public/`、`dist/` 或同步资料。建议把 Certbot 的 `config/work/logs` 放在用户私有配置目录，例如 `~/.config/<project>/acme`。

DNS-01 hook 只能维护本轮需要的 `_acme-challenge` TXT 记录；创建后等待权威 DNS 和公共解析可见，清理时只删除本轮记录。OSS 证书更新应使用自定义域名证书接口绑定到具体域名，不把私钥作为普通对象上传。

交付状态必须拆开描述：脚本已写好、手动跑通、证书已上传绑定、HTTPS 已验证、定时任务已安装、定时任务已实际自动执行，是六种不同证据。Mac 的 `launchd` 或本机 cron 依赖开机和联网，不能等同于服务器级高可用续期。

## GitHub Actions 云端续期

用户选择云端 SSL 续期时，建立独立于网站发布的 workflow，复用 `ops/ssl-renewal/` 中可审查的脚本。使用 GitHub 托管 runner 或已确认常驻的云端 runner，不把用户 Mac 的 self-hosted runner 当作无需开机的方案。此处是实施指引，调用技能不自动授权新增 Secrets、DNS 操作或证书绑定。

- **触发与调度：**提供 `schedule` 和受控 `workflow_dispatch`，限定实际默认分支和授权域名；说明 cron 时区及运行时间，可每日检查是否需要续期，避免每次强制重签。workflow 必须在默认分支；定时执行可能延迟或漏跑，不能保证准点。核查 Actions 可用性、额度与禁用状态，公共仓库还需注意长期无活动导致定时停用。为到期阈值及久未成功执行设置可核验告警，通知对象和方式按授权配置。[GitHub 调度说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
- **隔离与凭据：**网站上传身份、DNS 验证身份和证书绑定身份分别按所需 API 配置；上传 RAM 的 GetObject/PutObject 权限不代表能绑定证书。用户本人安全输入凭据，采用实际可用的受保护环境或身份联合；GitHub token 默认最小权限，第三方 Actions 固定审查过的 commit，运行时禁止打印秘密和 shell trace。PR/不可信代码不能得到续期秘密，保留 GitHub 协作文件所述 workflow 写权限风险。环境审批若每次需要人批准，应明确这是有人值守续期，不能声称无人值守。
- **持久状态：**临时 runner 不能仅依赖本机 Certbot 目录。明确 ACME 账户、renewal 配置、证书及私钥的受控恢复/保存方案，可使用经授权的独立私有加密存储并验证备份和访问范围；不放源码、普通 Actions artifacts/cache 或公开站点桶。避免每轮从零申请而触发 CA 限制。限制临时目录权限，在结束时清理；状态保存失败要报失败，不能仅凭证书绑定成功称完整续期成功。
- **执行链：**恢复状态 → 环境/目标预检 → DNS-01 验证与按需续期 → 校验证书 SAN、有效期、证书/私钥匹配 → 在已授权范围备份现有绑定与可恢复证书 → 经 OSS 自定义域名证书 API 绑定每个目标域名 → 无忽略 TLS 错误的 HTTPS 与真实根路径 GET 验证 → 安全保存更新状态。DNS hook 只操作本轮 TXT，传播等待有超时，失败清理仅删除本轮记录。HTTP-01 仅在已验证适用时沿用前节流程。证书不作为普通 OSS 对象公开上传。
- **幂等与恢复：**按站点/证书设置并发互斥，避免同时续期或覆盖状态，不取消正在绑定/保存状态的运行。先做 CA staging/dry-run 验证，测试证书不能绑定生产；再完成授权的正式手动运行。按需使用 deploy hook，但还应比对线上证书，支持补做上一轮失败的绑定；Certbot `renew` 退出成功可能表示无需续期，不能据此声称新证书已签发。[Certbot 续期与 hooks](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)
- **失败与验收：**校验失败不覆盖有效证书；绑定后核验失败按已授权且确实可恢复的方案回滚，不自行改 ACL、Policy 或 DNS 路由。记录 commit、Actions run、执行方式、每域名证书序列/指纹与到期时间，不记录私钥。区分 workflow 已写、调度已启用、手动运行成功、定时已实际执行、无需续期、新证书签发、绑定成功、HTTPS 验证成功及状态持久化成功。等到有定时 run 证据才能确认自动执行；此前标注未验证，并交接到期监测、责任人和紧急手动恢复步骤。

## HTTPS 与续期是另外两步

申请完成后，按授权把证书通过 OSS/实际 HTTPS 终结点的证书配置接口绑定至每个已配置自定义域名；私钥不作为普通 OSS 对象上传。检查各域名的 TLS、页面、资源、404。确认有效后才按约定配置 HTTP→HTTPS 或主域名跳转，并保持验证路径可用。

若设置自动续期，须分别落实并验证：定时执行器、验证钩子、续期本身、导出同步、云端证书更新和失败通知。Mac 休眠/离线时本机调度不能保证及时执行，应明确运维责任或选择稳定环境。只有命令或 hook 文件时写“具备续期路径，未设置自动调度”，不能称“自动续期已完成”。
