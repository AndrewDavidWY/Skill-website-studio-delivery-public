# 生产版本核验：从 PR 到线上页面

在任务需要确认“这个改动是否已经上线”、发布后验收或交接生产版本时读取。只检查用户指定的站点与发布范围；核验请求本身不授权合并、部署、回滚、清缓存或修改权限。

## 1. 固定本轮对象

记录仓库、目标分支、PR、目标改动、预期生产域名、部署环境、核验时间及允许执行的操作。先实时读取远端，不把旧工作目录、截图或预览站当生产依据。目标分支移动时保留原记录，并注明新旧基线。

区分两个问题：
- **版本一致**：线上是否是指定提交构建的产物？
- **功能存在**：较新的线上版本是否包含该改动，且实际行为正确？

后者不能冒充前者。PR 源分支 SHA、合并提交 SHA、构建 SHA 可以不同；squash/rebase 后通过合并记录、提交关系及改动内容建立对应，不能机械要求所有 SHA 相等。

## 2. 建立五层证据链

| 层级 | 最小核验 | 不能据此推断 |
| --- | --- | --- |
| PR / 代码 | PR 状态、最终合入提交、目标分支、预期文件差异 | merged 不表示部署完成 |
| 构建 | 精确提交对应的运行 ID、attempt、结论、构建配置、产物 ID 或摘要 | 其他 SHA 的绿灯、上传成功不表示本次可用 |
| 发布 | 实际生产环境的部署记录、提交/产物关联、时间、结果、目标域名 | preview、staging 或队列已受理不等于 production |
| HTTP / 文件 | 最终 URL、状态、重定向、页面关键内容、实际引用的 CSS/JS/图片等资源 | 200、首页可开、单个版本标记不证明整站一致 |
| 用户行为 | 受影响页面与关键交互、设备/语言范围、控制台和网络错误 | 本地通过、截图好看不表示线上操作正确 |

按实际发布流程记录适用层级：未使用 PR、独立 CI 或构建服务时标明不适用，并记录实际源码、构建与上传版本之间的关联；不为核验另建流水线，也不能把本应存在却缺失的证据标成不适用。

优先保留系统现成的不可变证据：commit SHA、运行/部署 ID、产物 digest、带 hash 的资源名和公开 build manifest。版本标记只是交叉证据；不要为了验收擅自新增公开诊断端点或泄露路径、环境变量、密钥。

没有部署 API 或版本标记时，可对照构建清单、线上正文与资源摘要，说明间接证据能支持什么。若 CDN、压缩、HTML 转换等让字节摘要不可比，改核对可比的构建标识及功能，不伪报 hash 一致。

## 3. 核对生产响应与缓存

- 从批准的生产域名开始，记录重定向最终地址，排除预览站、旧子域名和错误环境。
- 至少覆盖改动页面、关键入口、受影响语言路由及其真实引用的资源。检查软 404、错误页返回 200、旧 HTML 引用已删除资源、MIME/加载失败和跨语言错配。
- 记录响应时间及有助于解释版本的缓存头、ETag 或 Age；不把这些头单独当提交证明。必要时比较普通访问与项目允许的重新验证请求。查询参数或硬刷新不保证绕过所有缓存。
- 增量发布时核对本次清单、删除项处理及未改动文件依赖。部分上传成功不能宣告整站一致；避免清理仍被旧缓存 HTML 引用的资源。只在既有发布流程与授权内采用原子切换或回滚。
- 若部署正在排队或 CDN 传播中，记录 pending，按实际发布窗口继续检查。若线上回滚、出现新部署或目标提交变化，重新确认当前证据链，不混用不同批次的结果。

## 4. 验收、停止条件与交付

在本轮范围内，只有适用层级的证据相互对应且关键线上行为通过，才说“已上线并验收”。条件只满足一部分时使用明确状态：代码已合并 / 构建通过 / 部署处理中 / 线上版本未确认 / 线上行为失败 / 已上线并验收。

监测持续到目标条件达到、部署终止、用户指定的窗口结束、目标被替代，或需要新的授权/输入。窗口结束但没有证据时结论是未确认，而不是通过。不会因为重复看到 pending 就自行宣告完成；也不以重复部署替代诊断。

交付记录使用 [production-verification-report.md](../assets/production-verification-report.md) 的字段。保留源链接、SHA、UTC 时间、执行命令/观察、实测范围、未跑项与原因。公开报告只保留可公开证据，不附内部日志、账号、cookie、客户内容或凭据。发现问题时给出可复现步骤和最小下一步；修复、重发和回滚仍遵循原授权。
